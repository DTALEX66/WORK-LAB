# WORK-LAB 跨软件 · 跨项目 · 跨环境通用工作流任务包

**2026-09-16 · R1 · 差集规划 · 本轮不执行仓库或软件修改**

> WORK-LAB 是建设维护方；所有获准接入的项目和工作流软件都是消费者。不是只在 WORK-LAB 仓库内同步，也不是 ChatGPT→Codex 专用桥。

## 1. 本轮最终目标

在原始五维基线、官方原生接口与用户配置下，实现：**选定审计/任务定稿 → 发布冻结版本 → 对应项目/环境自动领取 → 原生软件执行 → 结果回传 → 其它审查端回读 → 任务修订和继续执行**。共同规则、技能插件和版本适配同时由通用机制维护，项目业务数据与权限隔离。

用户不再承担正文复制、下载后转发、回贴日志和反复解释已完成事项。必要的范围批准仍保留，既有有效授权不因换软件而被重复索取。

不要求后台“监视所有聊天”：只处理用户明确发布的任务工件；当前聊天结束后也不会自动被本地事件唤醒，除非另有受支持且已批准的复核触发。

## 3. 五维基线：保留，不发明替代版本

| 维度 | 本包约束 |
|---|---|
| 唯一权威入口 | 使用官方发行/认可入口；同一安装的 GUI/CLI 不被误判为重复安装 |
| 桌面入口 | GUI 按真实快捷方式验证；CLI/云端按适用性验证，不伪造桌面程序 |
| 官方标准＋用户配置 | 原生格式/权限不绕过；用户模型、推理、认证、未知字段保留 |
| 轻量不阻塞 | 按需规则/技能、增量同步、0 空闲模型轮询；故障只隔离受影响任务 |
| 任务级模型策略 | 质量/成本/隐私/延迟在任务层；不新增全局日/月费用上限或强制推理档位 |

五维来自固定 SHA 的根规则。第四维意味着减轻重复治理，不是取消真实权限和验收。[R2]

## 4. 技术取舍与通用性保证

**采用：**项目自己的 GitHub 原生 API/官方 MCP 作为首通道，已有本地任务/回执设施处理认领；不同软件走各自原生入口；第二通道用不可变文件包，验证非 Git 与非 GitHub 使用。[W1–W6,W9,W10]

**可选：**Linear、n8n 为其它业务平台连接；Vibe Kanban 仅在需要替换相同职责模块时验证；Symphony 作为工程预览参考。不是把四套系统叠进默认运行链。[W7,W8,W11,W12]

新增项目主要靠登记，新增软件主要靠薄 Adapter；未知的闭源接口不能保证完全自动化。逐能力列出已验证/部分/未支持，不能把部分支持冒充全覆盖。

## 5. 分批顺序和先交付的价值

| 批次 | 工作 | 可声称的结果 |
|---|---|---|
| 0 | 差集锁定、规则边界、项目绑定、格式兼容 | PLAN_READY，尚未开通同步 |
| 1 | 云端发布、持久领取、适配器、真实执行、回传 | ONE_REAL_FLOW_VERIFIED，解决第一条真实搬运痛点 |
| 2 | 修订取消、软件入口、第二通道、跨项目、节点接管、规则与 Observer | 通用范围逐项实证；不能只用模拟场景 |
| 3 | 版本差分、精确测试、薄部署与最终验收 | 所声明范围全部满足后 UNIVERSAL_WORKFLOW_VERIFIED |

设计与合成测试在授权范围内可先行。A/B/Adapter 的开发可在各自工作树并行；共享 schema/存储迁移由一个写者先落，不要多人同时修改同一文件。全局部署、外发、费用不足只暂停对应真实分支，不逼迫所有任务等待。
