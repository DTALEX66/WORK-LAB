# 全局项目执行标准（Global Project Execution Standard）

> WORK-LAB 负责的全局层规范——一套执行标准，适配所有软件 + 所有项目。
> 依据：2026-08-23 调研（AGENTS.md best practice / SKILL.md 触发机制 / 并行 agent 编排）。
>
> **治理最小化原则（硬约束，优先级高于下文所有步骤）：**
> 1. 治理是最小护栏，不是每步设卡——检查只在【落地前一次】，执行中途不查
> 2. 建议性检查（质量提示/可选门禁）fail-open：失败/超时不阻塞执行，只报告，绝不循环重试；
>    安全与权限检查（凭据、数据边界、越权写入、发布内容校验）**fail-closed**：失败即阻断，不因超时放行
> 3. 工具按需用（可选），不强制每个任务全跑；未命中的检查直接跳过
> 4. 禁止元治理循环（检查的检查、漂移收敛再漂移的死循环）
> 5. 加任何机制前先问：它让执行更快还是更慢？更慢就不加

## 一、三层结构定位

```
① 全局层（本文档）：一套执行标准，所有软件 + 所有项目共同遵守
② 项目层：各项目 AGENTS.md + SKILL（各自内部，引用全局标准）
③ 软件层：各软件自身配置
```

## 二、执行生命周期（一个任务怎么跑）

```
① 任务理解 → ② 技能扫描(按需，fail-open) → ③ 任务分片 → ④ 执行 → ⑤ 验证 → ⑥ 落地
```

| 步骤 | 动作 | 要点 |
|---|---|---|
| ① 任务理解 | 明确目标/边界/验收标准/非目标 | 不明确先问 |
| ② 技能扫描 | 查索引（未命中才扫），命中即加载 | fail-open，未命中直接干 |
| ③ 任务分片 | 大任务拆独立单元 | 可并行分片 |
| ④ 执行 | 按技能 + 项目规则干活 | 遵守全局边界 |
| ⑤ 验证 | 按变更域跑相关测试 | 不全量一刀切 |
| ⑥ 落地 | 一次性检查（漂移+审计合并）| **fail-open：检查失败只报告不阻塞**，绝不循环重试 |

### 多轮任务防漂移（落地前必查）

```
多轮任务后项目可能漂移（基线 vs 实际偏离），落地前检查一次：
  流程：record_baseline（干净验证后记基线）→ check_drift（对比当前 vs 基线）→ converge（确认新基线或修复后重记）
  漂移 → 先报告/收敛，不直接落地；干净 → 才允许合并
  注：历史上引用 10-workflow/workflow-assistance 的脚本路径已于 2026-09 目录收敛后失效
  （10-workflow/ 不再被 Git 跟踪）；漂移判定以 CI 门禁 .github/workflows/work-lab-gate.yml
  内的 services/orchestration/run_quality_gate.py 为准，不再手敲死路径。
```

## 三、技能按需调用（fail-open）

```
各软件执行任务前按需走步骤②（命中才加载，未命中直接执行，绝不阻塞）：
  1. 先查项目技能调用索引（.hermes/skill-call-index.json）
     → 命中 → 直接调用技能（不重复扫描）
  2. 索引未命中 → 扫描技能清单（SKILL.md description）
     → 匹配 → 加载技能执行 + 记录到索引（下次直接命中）
  3. 仍未命中 → 直接执行（不阻塞）

技能调用索引（优化，避免每次扫描；文件按需生成，fail-open）：
  索引：.hermes/skill-call-index.json（首次扫描后落盘；不存在时直接扫描 SKILL 清单）
  机制：build（扫描建关键词→技能映射）/ lookup（任务关键词查索引）/ record（学习新映射）
  每项目一个索引文件，后续相同任务直接调用；索引缺失/损坏时降级为全量扫描，绝不阻塞

触发机制（借鉴 Claude Code skills）：
  model-invocable：description 语义匹配，模型自动调用
  user-invocable：用户显式调用
  项目规则（AGENTS.md）明确：执行前先扫描 SKILL
```

## 四、并行执行（替代单写者）

```
任务分片（③）→ 每分片独立 worktree 并行写 → 审计（⑤）→ 队列合并（⑥）
- 单软件项目内多实例并行
- 多软件同项目分任务并行
- 路径级所有权（advisory 认领，重叠才排队）
```

## 五、全局边界（所有软件+项目遵守）

```
1. 安全：非明确授权禁止访问 E:\ 数据盘
2. 数据边界：各项目构建缓存/产品资产留在自己项目内，禁止外溢/漂移
3. 官方优先：软件更新以官方发布为准，禁私自本地打包
4. 模型中性：provider/model/reasoning 跟随用户原生选择，low/medium/high 本身非故障；不设全局限速/限流/降级，不后台覆写用户选择
5. 审计分层：按变更域跑（不全量一刀切），合并前全量
```

- 各项目 AGENTS.md 引用本文档（不重复写全局边界）
- 各软件通过 hook/引用加载此标准

## 七、NF-01 材料/遥测边界澄清（2026-09-16，追加不改原义）

原"项目 Git 根内"与"禁止 prompt/response bodies"是宽泛表述，澄清如下（五维原义与第 1–5 条安全边界不变）：

1. **可流转**：用户主动选定要发布的业务工件——审计/任务文档、不可变任务包引用、回执引用——可在授权目标材料空间合法流转。白名单语义见 `packages/client-neutral-core/scripts/artifact_flow_policy.py`（`ALLOW` 分支）。
2. **永不自动镜像**：私人会话库、原生对话日志、Telemetry 正文、凭据、账号密钥、浏览器数据（`REJECT` 分支）——即使带 `authorized` 标志也拒绝；Telemetry 只留引用与最小元数据。
3. **未知类别 fail-closed**：不在白名单的类别不自动传输（`PENDING_AUTHORIZATION`）。
4. **嵌套秘密仍隔离**：白名单字段里埋藏的凭据/高熵 token 值仍被 `ISOLATE` 隔离，不泄漏到日志；只删顶层 key 不算合格。
5. **项目偏好不串项目**：项目 A 的临时离线/模型偏好（`scope=project/task`）不成为 B 的全局强制（`effective_for_project` 返回空）；刻意 `global` 是独立授权，可报告但不自动应用。

此澄清不新增任何全局费用/限速上限，不改用户模型/推理/认证原生选择。对照测试：`tests/workflow-assistance/nf01_rule_semantics_artifact_flow.py`（18 例）。
