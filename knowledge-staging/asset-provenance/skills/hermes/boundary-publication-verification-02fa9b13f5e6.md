# Boundary and publication verification

## Purpose

Use this skill when a project has runtime/build/test artifacts outside its repository, when user-home state may belong to a project, or when a remote push must be visible to GitHub/web consumers. The goal is not merely to move files or push commits: prove ownership, containment, exact remote state, and consumer visibility without claiming more than the evidence supports.

This skill complements the protected `project-data-boundary` and `github-pr-workflow` skills. Follow their stronger rules when loaded; this skill records the cross-cutting checks that are easy to miss between them.

## 1. Classify ownership before changing anything

Use four buckets:

1. **Current project-owned** — source, generated runtime, SQLite, evidence, logs, caches, test data, and build outputs belonging to the current Git root. Keep these under `<project>/.hermes/task-runtime/` or the repository's established ignored runtime paths.
2. **Project external environment** — installers, SDKs, portable tools, shared environments, and related machine configuration. For Cognitive-Loop-OS, manage these under `D:/All projects/OS configuration`; do not copy them into the repository or user-home Temp.
3. **Shared workflow/system state** — Hermes, Gateway, authentication, sessions, scheduler, browser-wide state, and user-level startup configuration. Preserve in the owning global location unless exact ownership and a supported migration procedure are proven.
4. **Other or ambiguous project** — a separate Git worktree, remote, dirty checkout, or personal data. Do not move, delete, or rewrite it merely because its name resembles the current project. Record it as unresolved and request an exact-path decision if disposal is required.

Never scan or modify protected drives outside the current request. Do not read secret values; record only `[REDACTED]` when credentials are encountered.

## 2. Read-only discovery first

Before migration, collect a compact manifest containing path, type, size, modification time, Git root/remote when applicable, active-process evidence, and candidate ownership. Prefer targeted marker scans over dumping a whole user home. For runtime profiles, inspect only metadata and process command-line booleans; do not read cookies, browser databases, or credentials.

For every candidate, answer:

- Is it definitely generated by this current project?
- Is it active or recently modified?
- Does the authoritative target already exist?
- Is the source a separate repository or dirty worktree?
- What exact rollback path exists?

A failed delete or partial move is not success. Re-scan the exact source prefix after every side effect.

## 3. Test and temporary-data containment

Environment variables alone may not contain pytest on Windows. `pytest` or Python `tempfile` can cache the system Temp root before project fixtures run. For project tests:

1. Set `TMP`, `TEMP`, and `TMPDIR` to `<project>/.hermes/task-runtime/pytest-tmp` in the real `tests/conftest.py`.
2. Explicitly set `tempfile.tempdir` to that same directory.
3. Set `PYTHONPYCACHEPREFIX` to `<project>/.hermes/task-runtime/pycache`.
4. Add a regression test asserting both `tempfile.gettempdir()` and pytest `tmp_path` are relative to the project task-runtime root.
5. Run the regression RED before changing the fixture, then GREEN, then the full suite.
6. After tests finish and no pytest processes remain, remove only exact, verified project-owned spill directories under the user Temp. Never delete the whole user Temp or unrelated `pytest-of-*` data.

For commands outside pytest, use the project-data wrapper so caches, artifacts, logs, Playwright data, UV/PIP caches, and Python bytecode are injected into ignored project paths.

## 4. Runtime profile migration and cleanup

For a desktop/WebView profile:

1. Confirm the runtime source code's authoritative development and installed data roots.
2. Confirm the target directories exist and are writable.
3. Confirm no active process uses the old profile path.
4. Compare source/target metadata without opening browser data.
5. If the target already contains the authoritative profile and the old source is inactive/stale, remove only the exact old profile after recording the evidence. Do not migrate cookies or browser state into a project checkout just to make the path look tidy.
6. Re-scan the old prefix and run the runtime's cold-start/readback smoke before claiming the boundary is repaired.

Shared AppData, Hermes, Gateway, WebView2, and startup paths are not automatically disposable. A product-like directory name is evidence for inspection, not permission for recursive deletion.

## 5. GitHub upload versus consumer visibility

A successful `git push` proves only that a remote ref was updated. It does not prove that the repository default branch, a PR, GitHub Actions, or a ChatGPT/web repository connector can see the change.

After pushing, verify:

```bash
gh api repos/$OWNER/$REPO --jq '.default_branch'
git ls-remote origin refs/heads/main refs/heads/$BRANCH
gh pr list --repo $OWNER/$REPO --head $BRANCH --state all
gh api repos/$OWNER/$REPO/commits/$SHA --jq '.sha + " " + .html_url'
```

Report separately:

- repository metadata/description updated;
- feature branch ref uploaded;
- PR created and its base branch;
- exact head SHA and CI checks;
- default branch merged;
- downstream connector/index refreshed.

If the SHA exists only on a feature branch with no PR, state that default-branch readers may still show old content. Do not change the default branch as a shortcut without explicit authorization. The durable visibility path is PR → exact-SHA checks → merge to default branch → connector resync.

## 5.1 Public description and error-summary synchronization

When the user asks to update all cloud/public descriptions or publish an error summary, treat the repository metadata, README, project-definition entrypoint, troubleshooting docs, and relevant PR bodies as one public surface. First read the current local text and GitHub metadata; then establish one truthful project identity and separate completed evidence, non-blocking upstream warnings, and unverified future-project coverage.

For audits that diagnose a desktop/CLI tool outside the repository, keep the boundary explicit: publish the repository-controlled findings and redacted verification evidence, but never copy user-level auth/config backups, cookies, browser state, or private profile contents into the project. A request to “upload to the repository” means push and open/refresh the PR unless merge is separately authorized; report the PR head SHA and exact checks, and do not call the feature branch merged. In particular, **do not tell the user “云端描述文件已更新 / GitHub 已更新” as if it were done while the change only sits on a PR branch** — the default-branch view still shows the old content, and the user will (correctly) report “GitHub 上还是一样的”. Only claim an update after the merge to `main`, then prove it by reading the remote, not the local cache: `gh api repos/$OWNER/$REPO/contents/docs/... --jq '.[].name'` and fetch the merged `README` and grep for the added section. Treat “已推送 (pushed)” as a distinct lower claim from “已更新主分支 (merged & visible)”; never conflate them in the final report.

Use this sequence:

1. Add a repository-local class-level error/decision summary for non-trivial corrections. Do not include credentials, auth stores, private live paths, session data, or speculative claims.
2. Remove stale or unsafe examples such as plaintext `.env` writes, global configuration as the default, fixed user-profile paths, and unapproved credential handling.
3. Run `git diff --check`, security/documentation scans, affected tests, and the canonical quality gate when governance, portability, safety, or release claims change.
4. Update the GitHub repository description only after local validation. Do not hardcode an arbitrary Node/action/runtime choice to silence an upstream annotation; record the warning as upstream and preserve the project’s reproducible CI contract.
5. Update an existing merged PR body only to correct or complete its historical record. Use a new PR for repository files and verify required checks against the new PR head SHA.
6. After merge, read back the merge SHA and main-branch workflow; require `headSha == mergeSha`, successful required jobs, `HEAD == origin/main`, a clean tree, and readback of the repository description and relevant PR bodies.

The reusable command/readback matrix is in `references/cloud-description-publication.md`.

## 5.2 Canonical positioning and public description readback

When the user supplies a repository README, handoff, or explicit positioning text as the canonical identity, treat it as authoritative over any earlier agent summary or inferred project framing. First extract the identity boundary and non-goals: client-neutral versus product-specific, governance/observation versus execution, and which external runtimes remain outside the repository. Update the repository metadata description to a concise form of that canonical statement; do not broaden it into a generic monorepo or task-control description that changes the product identity.

After a metadata write, verify consumer visibility in three separate layers:

1. authenticated GitHub API (`gh api repos/OWNER/REPO`);
2. anonymous public REST API (`curl https://api.github.com/repos/OWNER/REPO`), without credentials in the URL or output;
3. public repository HTML/title via a browser or equivalent public fetch.

Report the exact description returned by all three. If API and public HTML agree but a user's existing tab shows stale text, classify it as client/browser cache and provide a hard-refresh or fresh-URL check; do not repeat arbitrary writes. Keep repository description, root README, module README and project-definition docs synchronized only when each is intentionally part of the same public identity surface. A metadata update proves description visibility, not code publication, commit, merge, CI, or live deployment.

## 5.3 Canonical project reload before cross-repository publication

When a task involves an external platform checkout plus a canonical project repository, reload the current project's `AGENTS.md`, root README, module allowlist, and task-pack scope before interpreting words such as “撤回官方推送” or “推送到本项目仓库”. Treat these as separate ownership domains:

1. Verify whether the external commit actually exists on its remote before planning a withdrawal. If it was never pushed, report withdrawal as a no-op; do not invent a remote rollback.
2. Identify the canonical repository and allowed module roots from live project files, not from the external checkout's branch or commit message.
3. Do not absorb or copy global platform state, user-home repositories, credentials, sessions, providers, or external runtime source into the canonical project merely because the user says “project repo”. First locate an explicit task-pack path and ownership contract; otherwise preserve the external artifact separately.
4. A project-local push proves only the canonical project commit was published. Report external repair commits, canonical project commits, remote refs, PR/merge state, and CI as separate evidence dimensions.
5. If the requested publication target is ambiguous after reload, stop before cross-repository copying or remote mutation and state the exact target/reason for the boundary decision.

This prevents a validated external fix from being mistaken for a canonical product deliverable, and prevents an imagined official push from being “retracted”.

## 6. Verification and final report

Run the smallest relevant checks, then the full gates:

- boundary regression and full pytest;
- Ruff/import checks and architecture/convention guards;
- Rust/desktop tests when runtime paths changed;
- browser and HTTP smoke with project-local `COGNITIVE_DATA_DIR`;
- exact source-prefix re-scan and active-process check
- `git diff --check`, explicit `git status`, and remote SHA readback

## Verification checklist

- [ ] repository description, README, troubleshooting/error summary, and relevant PR bodies agree
- [ ] merge-SHA main CI is verified separately from PR-head CI

Final reports must distinguish **moved**, **removed**, **preserved**, **unresolved**, **pushed**, and **merged**. Do not turn a description update into a claim that code was uploaded, and do not turn a feature-branch push into a claim that web consumers indexed it.
