# Probe — 紧凑 HUD 的可用性验证计划（未执行）

- **生成时间**：2026-10-19
- **状态**：**计划，不是研究结论**。本轮没有招募、没有访谈、没有观察记录。
- **样本现实**：本仓只有 1 位 owner/operator，不存在外部用户池。因此下文的
  "n=1 owner walkthrough" 是**冒烟测试**，不能代表用户研究；结论只能用于发现明显误解。

## 1. 要验证的 3 个假设

| ID | 假设 | 若被推翻，说明什么 |
| --- | --- | --- |
| H1 | 用户能在 3 秒内区分 `LIVE` / `LIVE · 采样已过期` / `UNVERIFIED` / `OFFLINE` | 状态胶囊的信息架构失败，需要更强的形状/位置差异，而不是只改颜色 |
| H2 | "其他 7 个来源"会被理解为**聚合摘要**，不会被当成一个真实 provider | 聚合卡的命名/虚线/说明不够，需改文案或改为"查看全部"入口 |
| H3 | 44px 图标搜索仍可被发现（hover/快捷键/命令面板） | 发现性不足，需要空态提示或一次性引导 |

附加观察（不设为假设）：`覆盖 3/4` 的含义是否会被追问（对应 CHK-01）。

## 2. 方法

- **类型**：moderated task-based walkthrough（主持式任务走查）
- **对象**：owner 本人（n=1）；如未来有 2–3 位同行可加入，但本轮不假装有
- **环境**：headless 状态页或真实 Tauri 窗口（二选一；优先真实窗口以同时验证窗口层）
- **时长**：20 分钟
- **记录**：只记任务答案、耗时、原话（经同意）；不录屏、不采集个人数据
- **主持原则**：不引导、不解释 UI、不替用户读文案；用户问"这是什么"时回答"你觉得呢"

## 3. 任务脚本

| # | 场景 | 任务 | 成功标准 |
| --- | --- | --- | --- |
| T1 | baseline（LIVE） | "这个面板现在告诉你什么？总量是多少？" | 3 秒内读出总量；说出"本次快照"而非"今天累计" |
| T2 | stale | "如果现在要引用这个数字，你会怎么描述它？" | 说出"采样过期/不是当前"，而不是 plain LIVE |
| T3 | many（9 源） | "谁占得最多？'其他 7 个来源'是什么？" | 指出 78% 的来源；把聚合卡理解为摘要而非真实 provider |
| T4 | many | "想看被折叠的 7 个来源，你会怎么做？" | 找到顶栏「完整」或命令面板 |
| T5 | baseline | "'覆盖 3/4' 是什么意思？" | 说出"项目"或明确说"不确定"（后者即 CHK-01 复现） |

## 4. 追问脚本（5 问）

1. 你第一眼看到的是哪个元素？为什么？
2. 这个数字是"现在"的，还是"某个时刻"的？你怎么判断？
3. 如果它过期了，你希望它怎么告诉你？
4. "其他 7 个来源"和左边的 codex 卡，在你看来是同一种东西吗？
5. 如果只能保留一个信息，你会删掉哪一块？

## 5. 判定与产出

- **H1 通过**：T2 正确 + 追问 2 能指出状态胶囊/时间戳。
- **H2 通过**：T3 明确说"是合并的/汇总"。
- **H3 通过**：T1–T4 中至少一次主动使用搜索或 Ctrl K，或在被问"怎么找"时能指出图标。
- **失败处置**：任一假设被推翻 → 在 `check.json` 增补 finding，并回到
  `flow-web-20261019.md` 的候选表，而不是直接改视觉。
- **记录模板**：

```
participant: P1 (owner)
task | answer | time | quote | pass/fail
T1   |        |      |       |
...
assumption verdict: H1 ? / H2 ? / H3 ?
new findings: CHK-xx
```

## 6. 伦理与证据边界

- 不伪造原话；Journey 中的"心声"保持为假设。
- n=1 的结果只能写成"owner 冒烟测试"，不得写成"用户研究表明"。
- 若未来扩到外部用户，需先解决招募、知情同意与数据留存位置（仓内 `.project-local/`）。
