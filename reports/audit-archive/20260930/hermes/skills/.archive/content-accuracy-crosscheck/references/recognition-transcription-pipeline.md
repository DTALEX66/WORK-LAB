# 识别转译管线设计：识别层与内容事实层解耦

> 来源：2026-08-11 会话扩展。本 skill 的 `content-accuracy-crosscheck` 处理"对已提取内容做全网交叉对比"。本文件记录的是**更上游的设计问题**：多格式内容（PDF/图片/音频/视频/Office）经"识别转译 → 全网验证"的管线应如何组织，才既省钱又准确。

## 两层验证模型（必须分开，永不混用）

| 层 | 回答的问题 | 方法 | 适用 |
|---|---|---|---|
| 识别转译层 | 文本转得准不准 | OCR/ASR/提取 + CER/WER 金标准对 | 文字提取、扫描OCR、音视频ASR |
| 内容事实层 | 转译出的内容对不对 | 全网交叉对比（权威来源） | 所有格式通用 |

- 识别转译置信度 **永不** 当作内容事实准确性。
- CER/WER 只衡量识别管线，不衡量文档内容；公开内容事实只靠权威来源交叉核验。两者独立、不可互相替代。

## 两个候选管线方案

### 方案 A：线性瀑布流（用户最初提出）
```
外置引擎识别(省token) → 模型辅助识别 → 模型完整识别 → 全网验证
```
优点：成本递增、准确性递增、直觉清晰。
问题：
1. 多数文件本地引擎一次到位，逐级爬升浪费 token/时间（缺少"够用就停"）。
2. 无准确性闸门——没有定义"何时该从本地引擎升级到 LLM"。
3. 把识别层与验证层绑死：很多内容（私人记录、非公开信息、转译噪声）根本不可全网验证，却被强制走验证。
4. 缺人工复核出口——验证不通过的点没有去路。

### 方案 B：分叉 + 门控 + 解耦（推荐）
```
识别转译层（CER/置信度门控）：
  ├─ 文字型（文字PDF/Office/HTML）→ markitdown/trafilatura → 质量够？
  ├─ 扫描型（扫描PDF/图片）→ OCR(EasyOCR等) → 置信度够？→ 不够才上模型辅助
  └─ 音视频 → ASR(whisper等) → CER够？→ 不够才上模型辅助

全网交叉验证层（内容事实，与识别层解耦）：
  ├─ 可查证事实 → 权威来源交叉对比（见本 skill 主流程）
  ├─ 争议/差异 → 记录差异，不自动覆盖
  └─ 不可查证内容 → 跳过验证，标注"无法全网验证"

待人工复核队列：验证存疑/冲突/低置信 → 进人工队列
```
要点：
- **按格式分叉**：不同格式走各自最省、最准的本地引擎，不统一逐级爬。
- **门控升级**：用准确性阈值（CER / OCR 置信度）决定何时升级到 LLM，这是省 token 的核心——本地引擎够用就绝不调用模型。
- **解耦**：识别层与验证层互不依赖，避免把不可验证内容硬塞进验证流程。
- **人工兜底**：存疑/冲突/低置信进人工复核队列，不自动覆盖。

## 门控设计的现实约束

- 理想门控用 CER 阈值；但**很多场景没有金标准对**（无 `*.truth.txt`）。此时用：
  - OCR/ASR 引擎自带的置信度分数；
  - 启发式（如识别文本非空、语言可检测、长度合理）；
  - 或"默认上模型一次，用模型质量评估决定后续是否回退本地引擎"。
- 不要在无金标准时伪造一个 CER 数字；如实标 `unverified` 或改用置信度门控。

## 让外部 AI 独立评审此类设计（提示词要点）

当用户要求把方案交给外部 AI（GPT/Claude）审核时，提示词应：
1. **明确禁止预设结论**——"不要因为这是中文输入就顺着我的倾向"。
2. 给完整背景：两层验证机制、已有本地引擎清单、项目铁律（记录差异/不可查证不验证/人工复核/不伪造/置信度≠准确率）。
3. **两个候选方案都完整呈现**（不能只给一个，否则外部 AI 无从比较）。
4. 用 5-6 个引导问题逼出深入分析而非敷衍：各方案问题、门控指标（无金标准怎么办）、全网验证边界（哪些不值得验证）、未覆盖盲点（多引擎冲突/融合/去重/失败恢复）、最终推荐设计。
5. 允许外部 AI 说"两种都不够好，应该这样"——保持真正开放。
