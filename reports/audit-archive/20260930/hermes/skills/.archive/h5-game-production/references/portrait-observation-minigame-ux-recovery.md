# 竖屏观察类小游戏：从“后台仪表盘”恢复为可玩界面

适用于 CCTV、找异常、值守、调度、安检等竖屏 Canvas 小游戏。重点不是某个题材，而是把复杂模拟器恢复成手机上一眼可懂的观察决策循环。

## 用户纠偏信号

当用户指出以下问题时，不要先用测试数、包体、状态数量或“功能完整”辩护：

- 文字看不清；
- 一眼不知道怎么玩；
- 布局像桌面后台缩小版；
- 提供的参考图没有真正落实；
- 整体有 AI 仪表盘感；
- 声光电不吸引、玩法不简单、不会自然教学。

正确响应顺序：承认组合/产品失败 → 量化真机字号和触控 → 对照参考图拆结构 → 重构核心循环 → 在官方开发者工具截图验证。

## 真机换算先于视觉判断

固定 750 设计宽 Canvas 必须按 `windowWidth / 750` 换算：

- 393px 屏比例约 0.524；设计 12px 仅约 6.3 CSS px，不可读。
- 主要玩法文字目标约 14–18 CSS px，对应 26–34 设计 px。
- 辅助文字不应承载规则，建议至少约 22 设计 px。
- 主按钮至少约 48 CSS px 高，对应 92 设计 px以上；关键双按钮可做 150–170 设计 px。

审查应输出实际 CSS 像素，不得只引用设计坐标。

## 观察类小游戏的首屏信息预算

首屏同一时刻只允许一个任务。推荐结构：

1. 顶部：时间、得分、连击；
2. 一句话规则；
3. 最大 CCTV/主场景；
4. 2–3 个可比较读数；
5. 两个大决策按钮；
6. 单行即时反馈。

首局隐藏或删除：四键驾驶台、更多操作分页、七格状态卡、常驻日志、多个资源条、微小英文诊断。复杂控制可在后续渐进解锁，不能和首局判断竞争。

## 核心循环必须可被一句话复述

例如：

> 核对画面和数据：一致放行，矛盾封锁。

判断核心是否成立：

- 玩家是在观察线索，还是读标题答案？
- 玩家是在选择处置，还是按黄色推荐键？
- 正常操作是否有收益，还是“什么都不做”最优？
- 视觉异常是否对应可解释的规则？
- 文案提示是否与代码接受的正确动作一致？

若标题、红框、独特警报声、资源骤降或推荐按钮只在异常时出现，它们都会泄题。判断前应使用中性标题、统一边框、统一到站声，并隐藏异常造成的安全值变化。

## 嵌入式教学：做一次，不讲一页

基础观察模式建议固定三班，而不是让随机调度决定新手是否看得懂：

1. 正常样例：规则提示“一致，点放行”；误点不扣分，题目保持。
2. 固定明显异常：必须使用真实画面与数据的具体矛盾（如画面楼层 09 / 主控楼层 06），提示“封锁”；误点不扣分且题目保持。
3. 独立判断：强制在第二班后快速创建，不受随机事件冷却挤掉；撤掉“点这里”、呼吸框和答案高亮。无论答对、答错或超时，都要把教学状态推进到“已完成”，避免永久卡在第三步。

基础 60 秒模式若核心乐趣是“观察并判断”，异常判断后优先由系统自动执行已有映射动作并播放 0.8–1 秒结果动画；不要为了复用控制台代码再要求一次缺乏决策价值的处置点击。复杂处置应进入后续高级模式，而不是污染首局两按钮承诺。自动处置不得额外给玩家不可理解的操作分数，并应在正确、误判和超时路径中清理异常，避免污染下一题。

### 超时不是边角分支，而是教学主路径

首三班必须按“完全不点击”再跑一遍。常见死锁是 `expireInspection()` 只把题目标记过期，却留下 `activeAnomaly`；随后普通巡检和异常调度都被 `!activeAnomaly` 守卫阻塞，界面永久停在不可点击的“系统处置中”。建议明确矩阵：

| 超时位置 | 必须结果 |
|---|---|
| 第一班正常教学 | 不惩罚，`tutorialStep 0→1`，暂停普通巡检，仍按计划进入固定第二班 |
| 第二班固定异常 | 不惩罚，`tutorialStep 1→2`，自动处置并无条件清除 `activeAnomaly`，随后推进第三班 |
| 第三班独立判断 | 按正式规则记超时，`tutorialStep 3→4`，退出教学 |
| 教学后的普通异常 | 记正式惩罚，自动处置并清除 `activeAnomaly`，下一巡检/异常仍能调度 |

自动处置最好集中为一个运行时 helper，让正确、误判、教学超时和正式超时复用。即使映射动作意外返回失败，也要 fail-safe 清除活动异常或进入明确可恢复状态，不能让调度锁死。至少增加一个执行**生成后的真实 bundle**的可注入时钟测试：不点击第一、第二班，断言固定楼层矛盾仍出现、超时反馈出现、随后第三班出现且不含“点这里”。仅测纯 `expireInspection()` 不足以覆盖运行时调度。

此外，新普通题不能继承上一异常的视觉压力或处置动画。打开普通巡检前重置 motion timeline，并让共享 `deriveVisualState()` 在 `inspection.kind === 'normal' && status === 'pending'` 时使用中性 anomaly visual（仍保留真实门开关、楼层、人数等物理状态）。否则逻辑上是正常题，CCTV 却持续 glitch，玩家会被错误视觉线索诱导封锁。

要求：

- 教学嵌在第一局，计时冻结或宽容；
- 玩家必须亲手完成前两次分类；
- 首次错误给近场、可读解释，不只改抽象数值；
- 第二班固定为最清楚、可比较的异常，不依赖随机抽样；
- 第三班必须按时出现且无答案高亮；
- 返回玩家不重复强制教学；
- 状态机测试覆盖完整推进链（例如 `0→1→2→3→4`）以及第三班答错/超时。

## 参考图不能只抄颜色

拆解并复刻参考图的结构属性：

- 主场景占比；
- 机械实体厚度；
- 按钮数量和重量感；
- 字号层级；
- 留白与装饰密度；
- 光源方向、材质、螺钉、压下反馈；
- 圆角尺度。

“黑底 + 绿色描边 + 小英文”通常仍是 AI 仪表盘。工业参考应体现实体金属面板、双层边框、螺钉、指示灯、少量重按钮，而不是大量均匀小卡片。

## 烘焙 HUD 素材处理

CCTV 合成图常带固定楼层、英文诊断和答案。不要用一块中央空黑卡粗暴遮挡：

1. 先裁掉固定顶部/底部 HUD；
2. 用有结构意义的顶部遮光罩覆盖残留；
3. 重绘运行时中文 HUD；
4. 将“画面读数”和“主控读数”空间分离，形成真正可比较线索；
5. 在正常、异常、移动、暂停帧中复核烘焙文字是否仍透出。

半透明遮罩会让 `STABILIZED`、固定楼层等幽灵文字透出；答案区必须完全不透明，再在边缘渐隐。

## 声光电必须语义化且不能泄题

- 所有班次使用同一到站/接入声，不能只给异常播放唯一警报声；
- 正确放行：许可铃、门关闭、马达离站、轻震；
- 正确封锁：金属锁止、短低频冲击、中震；
- 错误：短促下降音、重震、近场解释；
- 异常画面可有物理线索声，但不能所有异常共享一个“答案声”；
- 强闪不超过约 3 次/秒；静音时仍可理解。

## 抖音开发者工具 CDP 目标选择

开发者工具通常同时暴露多个 CDP target：VSCode 编辑器、工作台、MiniApp Webview、iframe 和 worker。不要用宽泛的“抖音开发者工具”标题匹配来点“编译”，它可能命中代码编辑器 target 并静默返回 `undefined`。

- **编译/预览工具栏**：选择 URL 含 `workbenchMode=workbench` 的工作台 target，再在 `button,[role=button]` 中按可见文字精确找“编译”。
- **游戏点击和截图**：选择标题 `MiniApp Webview` 的 target。
- **验证编译是否真正发生**：等待加载后截图，必须回到倒计时 60 的开始页；不能只把 JavaScript 点击返回值当成功证据。
- **避免直接 `location.reload()` 游戏 Webview**：它可能停在宿主白色加载页。恢复应回到工作台 target 触发真实“编译”。
- **时间加速要谨慎**：在错误 realm 覆盖 `Date.now` 既可能无效，也可能污染后续模拟器状态。结算优先使用可注入时钟的 VM 测试；若必须做真实 60 秒截图，就让工具实际运行并在结束后重新编译复位。

## 官方工具验证顺序

1. 开始页截图；
2. 第一班正常教学，以及误点后题目保留/资源不扣；
3. 第二班固定明确异常，以及误点后题目保留/资源不扣；
4. 异常判断后的自动处置反馈，确认没有第二层玩家按钮；
5. 第三班无提示独立判断；
6. 正确、错误、超时、成功/失败结算；结算时清空 `activeAnomaly`、`inspection`、移动状态和旧反馈，避免暗背景仍显示未处置异常；
7. 393×852 与 360×640；
8. 换算字号、按钮和有效场景占比；
9. 从平台的真实胶囊 API 读取边界，检查胶囊、刘海和手势区，不要固定猜一个右侧预留值；
10. 将开发者工具实际截图按比例置入审核要求尺寸，禁止拉伸或裁切玩法区；同步更新审核路径、商店文案和发布交接，清除旧按钮名/旧双层玩法说明；
11. 最后运行全量测试、目标 strict、合规、包体和统一发布门禁。

自动测试证明状态和命中区；官方截图证明排版和资产；真实陌生玩家才能证明“好玩”。三者不可互相替代。开发者工具白屏或状态污染时，恢复方式是重新触发真实工作台“编译”动作并验证开始页，而不是把白屏当成游戏故障。
