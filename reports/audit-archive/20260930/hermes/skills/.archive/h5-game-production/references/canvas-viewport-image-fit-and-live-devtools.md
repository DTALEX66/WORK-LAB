# Canvas 视口与素材适配：先锁布局，再决定图片变换

## 核心原则

用户指出“图片尺寸不合适、黑边需要补齐”时，先确认**哪个对象必须保持不变**：

1. UI/CCTV 容器是否是既定布局的一部分；
2. 用户要“完整画面”还是“铺满窗口”；
3. 是否接受裁切、非等比拉伸、留边、背景延展中的哪一种。

不要默认用 `contain`，也不要为了匹配图片比例改变既定 CCTV 容器高度。对于用户明确要求“图片适配 CCTV 窗口”的项目：

```js
// 保持 viewport/layout 不变；图片铺满现有窗口
ctx.drawImage(image, x, y, w, h);
```

这会做非等比缩放，但满足“不裁切、不留黑边、窗口布局不变”。如果不允许形变，则必须让用户在 `cover` 裁切、`contain` 留边、预处理/外延素材三者中选择，不能同时承诺“完整、无形变、无黑边、容器比例不变”。

## 四种模式及代价

| 模式 | 代码 | 优点 | 代价 |
|---|---|---|---|
| 铺满/拉伸 | `drawImage(image,x,y,w,h)` | 无黑边、无裁切、容器不变 | 可能形变 |
| Cover | 等比放大后裁切 | 无黑边、无形变 | 会裁掉主体边缘 |
| Contain | 等比缩小居中 | 完整、无形变 | 会留黑边/空白 |
| 素材外延 | 预处理成目标比例 | 可兼顾完整与无黑边 | 需要重新生成/补画素材 |

## 禁止的错误修法

- 为适配横图而缩短/改变核心 CCTV 窗口，导致下方出现巨大空白；
- `contain` 上再叠低透明度 `cover`，产生双层电梯、重影和接缝；
- 看到黑边就提高背景亮度，而不检查容器比例；
- 连续猜测 `cover → contain → 改容器`，没有先复述用户想保持的对象；
- 只看单元测试，不在当前官方开发者工具窗口点进运行态截图。

## 正确迭代顺序

1. 用用户截图定位：黑边属于图片内部、Canvas viewport，还是外层手机/模拟器背景。
2. 复述约束：例如“保持大 CCTV 窗口，图片铺满它；不裁切、不留边”。
3. 先写回归测试：禁止旧 crop/cover/contain，断言目标 `drawImage` 方式；布局测试保持原 viewport 高度。
4. 修改 Renderer，不顺手移动读数、按钮或反馈区。
5. 构建正式 Douyin/WeChat bundle。
6. 同步到**用户当前已经打开的开发者工具项目目录**；不要重开开发者工具或切换工程，除非用户要求。
7. 在当前窗口自动编译后点击“开始”，截图验证：
   - CCTV 窗口大小未变；
   - 图片填满；
   - 无上下黑边；
   - 无双层重影；
   - 读数、双按钮、底部反馈仍在原位；
   - Console 0 runtime errors。
8. 再跑生成 bundle smoke 与全量测试。布局变化会使硬编码触摸坐标测试失效；优先让测试从布局函数导出坐标，避免魔法数字。

## 当前开发者工具控制注意

- 用户说“我现在开着，别重新开”时，绝对不要启动、关闭或重开工具。
- 先确认当前工程路径；若当前窗口指向 ignored 的本地工作副本，应同步经过验证的 `game.js/game.json/project.config/audio/visual` 到该目录，而不是另开根工程。
- 文件热更新后常回到启动遮罩；视觉验收必须再次点击“开始接管”。
- 自动化点击必须命中 Chromium renderer child window；顶层窗口消息可能落不到 Canvas。
- 自动化点击超时或坐标偏移造成的失败，不能归因于游戏逻辑；应立即区分自动化失误与产品缺陷。
