# 数据优先的调查游戏分阶段开发

适用于把简单“观察→二选一”玩法升级为“协议→调查→核验→处置→长期后果”，但用户暂时冻结视觉/UI 的场景。

## 阶段边界

### Phase 0：只读审计

- 记录分支、HEAD、工作树、最近提交。
- 执行依赖安装和全量测试；避免生成非必要 lockfile。
- 审计现有模块，防止重复创建已有地基。
- 只写审计文档，不混入玩法代码。

### Phase 1：纯逻辑地基

- 协议集合只评估对当前班次适用的规则。
- 调查工具只揭示证据，不返回答案。
- 单一工具来源不能定案；要求两个独立来源印证同一冲突。
- 热源、回放应有次数和资源成本；协议查询可免费。
- 多摄像头逻辑按 camera ID 隔离证据。

### Phase 2：内容与连续性

- JSON Schema 明确 `category`、`roundType`、证据、协议标签和污染后果。
- 内容数量测试与跨引用测试并重：异常→正常变体、班次→乘客、事件链→内容。
- 身份核验应让胸牌、允许楼层和计数模式真正影响结果。
- 事件链错误写入持久 flag，完成时输出后续班次修饰符或污染增量。

### Phase 3：UI/Runtime 接线

如果用户冻结视觉，此阶段保持 pending，不要偷偷修改 Canvas、素材、布局或按钮。生成平台 bundle 以登记纯逻辑模块不等于完成 UI 接线。

### Phase 4：非视觉后果系统

可在 UI 冻结时继续：

- 错误决定提升污染并改变后续信息源可靠性，而不是立即结束；
- 严重污染仍保留至少两条可靠验证路径，不能随机改答案；
- 高危错误写入后续修饰符；
- 复盘时间线合并决定、事件链与污染历史；
- 结局按条件和优先级确定。

## TDD 纵向切片

每个新模块先写一个最小失败测试，再实现最小逻辑。例如：

1. 热源扫描消耗一次次数和电力，但结果无 `decision`；
2. 切换 CAM-03 只暴露 CAM-03 证据；
3. 单一热源线索不定案，两来源印证后才 ready；
4. 错误高危动作不 `gameOver`，而是加入 `nextShiftModifiers`；
5. 复盘精确统计正确/错误/准确率/污染峰值。

## 自定义 IIFE 构建注意

新增纯逻辑模块也必须加入 `build.js` 的模块列表并按依赖排序，否则 Node 单测通过但生成 bundle 缺失符号。拼接式 bundler 共享顶层作用域，应避免通用私有函数名冲突（例如多个 `cloneState`），改用模块特定名称。

## 交付声明纪律

分别报告：

- 纯逻辑模块完成；
- 内容和 Schema 完成；
- 已加入 bundle；
- 正式 runtime 调度完成；
- UI 玩家入口完成；
- 官方工具截图完成。

前 3 项不能替代后 3 项。视觉冻结期间应明确“可测试但尚不可由玩家操作”。
