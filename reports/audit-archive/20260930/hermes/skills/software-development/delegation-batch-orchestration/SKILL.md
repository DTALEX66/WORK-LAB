# Parallel Delegation Batches（delegate_task 多子代理编排）

## When to use

- User asks to push many independent tasks in parallel（"任务包全部开启/全部并行推进/全部推进，开始"）。
- Work splits into independent workstreams touching disjoint files/modules — serializing would flood context.
- Validated repeatedly on ArcheAxis TaskPack batches (deleg_149dd4e1, deleg_739fe7e6): 3 leaf children + main thread in parallel.

## Brief construction (children know NOTHING of this conversation)

Each task must be fully self-contained. A brief that assumes shared context produces duplicate work or guard-blocked loops. Include:

1. **Project root + branch + HEAD sha** (so the child can confirm state).
2. **Existing-facilities inventory** — every module already built that the child must REUSE, with exact file paths ("勿重复造"). The #1 failure mode is a child rebuilding what exists.
3. **Forbidden zones** — regions/files the orchestrator owns and is editing in parallel (e.g. a byte-patched CORS/middleware block in main.py): "不要动 X 区；若必须改，用 <specific pattern>（文件尾部追加 import+include_router）". This is what prevents edit collisions.
4. **Exact test command** (iron rule):
   `python "<guard-wrapper>" --project . run -- env -u PYTHONPATH uv run --frozen --group ci --group ci-adapters pytest <files> -q --tb=short -p no:cacheprovider`
5. **Discipline block**: ruff must pass (I001/UP035/F401/F541/UP009 → `ruff check --fix` then re-run tests); no shell chaining/redirection/absolute paths (guard blocks); `git add` only specific files; E-drive ban; temp files only under `.hermes/task-runtime/`; do NOT write project truth logs (orchestrator owns LOG entries — prevents concurrent LOG appends); scope every repo-wide search to source trees and explicitly exclude the controlled runtime dirs (`.project-local/`, `.hermes/task-runtime/`) — they hold multi-MB run snapshots, and one unscoped recursive grep floods the child's tool result and burns its context before it does any work.
6. **Evidence requirement**: "print the test command + passed count in your summary; list the files you git add'ed." Self-reports without numbers are worthless.
7. **Default-resolution clause**: children cannot ask questions — resolve ambiguity in the brief ("如无法 X，则做 Y 并说明原因").
8. **Keep each task payload under ~8K tokens; put the detailed spec in a file.** An over-large `delegate_task` arguments block times out the delivery stream (system note: "too large ... Do NOT retry the same tool call"). For multi-deliverable tasks with detailed specs, write the full spec to a scratch file first (project context, known facts, deliverable list, forbidden zones, exact verification commands, expected output shape — e.g. `.hermes/task-runtime/<task>_spec.md`), then make each task's `goal` a one- or two-line pointer: "read `<spec path>` and execute it", with only the task-specific slice named. The literal Windows drive letter (`D:/All projects/...`) is safe inside spec FILES — the guard's drive-letter block applies to wrapper command-line TEXT only. On project-data-boundary repos (WORK-LAB, ArcheAxis) put the scratch spec under `.project-local/task-runtime/<task>_spec.md` instead of `.hermes/task-runtime/` - the guard keeps task data in-project and may block `.hermes/` as an external path; `write_file` to that `.project-local/task-runtime/` path is the verified-working location.
9. **Valid `output_schema` (if you want structured returns).** `output_schema` is a real JSON Schema: array fields take `items` as an *object* (`{"type":"string"}`), never a bare string (`"string"`) — a bare-string `items` makes the whole schema invalid, and a child that otherwise succeeded still fails the batch with `Final answer does not satisfy the declared output_schema (after 1 retry)` even though its work is sound. Keep the schema forgiving: require only the fields you will actually read, mark the rest optional, so a partial-but-real result passes validation instead of being rejected wholesale. A schema rejection means "re-check/validate the schema," not "the child did no work" — inspect the child's disk output before re-dispatching.

## While children run

- Do NOT poll/wait — continue orchestrator-side work on files the children are NOT touching (e.g. docs, packaging, frontend skeleton, release workflows).
- **Do not mutate the branch or working tree while a child is live.** `git switch`, `git pull`, `git stash`, `git rebase`, or a bulk `git checkout` moves files out from under a running child, and its later `git status` / diff then reports someone else's churn as its own. Defer branch surgery, local syncs, and snapshot restores until the batch reports; when a child's uncommitted work must move to a new branch between batches, branch from the freshly merged `origin/main` AFTER the child has exited — uncommitted work rides across cleanly when the two trees are identical.
- **Allow only ONE live writer of the cross-cutting gates.** Two children sharing a
  working tree must not both run the repo's snapshot-writing aggregate (the authority
  chain, the report generator, anything that regenerates tracked artifacts): the second
  run rewrites what the first just recorded, and each child then reports a `DRIFT` the
  other caused — two contradictory reports you have to adjudicate against a baseline you
  cannot reconstruct. Name the single runner (one child, or the mainline after the batch
  reports) in every brief and give the others an explicit "do NOT run <that command>"
  line; the same instruction belongs in the sibling's brief when IT is the runner.
- Children finish at different times; the consolidated result re-enters the conversation only when ALL finish. Work as if they might take 10-20 min.
- Tail live transcripts via a SCRIPT file (the guard blocks inline absolute paths like `C:\Users\ALEX\AppData\Local\hermes\cache\...`). Transcripts live at
  `C:\Users\ALEX\AppData\Local\hermes\cache\delegation\live\<delegation_id>\task-{0,1,2}.log` — decode `utf-8` with `errors="replace"` (they can be UTF-16 or UTF-8 mixed).

## Verification (MANDATORY before commit)

- **Child summaries are self-reports, not facts.** Independently re-run each child's test files before committing. In LOG-178 the child claimed completion but its final full re-run never executed — the orchestrator's independent 55-passed run closed the gap.
- Check deliverables actually landed on disk (files exist, non-empty) — do not trust "created".
- **A child will resolve cases the brief never named — require those to be surfaced, then review them.** Ask for them explicitly (an `incomplete` / review-notes field in `output_schema`, or a "spec-silent decisions" list) and read each one before merge: the docstring plus the test that pins it, then either accept it in the PR body as a reviewed decision or change it. Shipping an unlisted behavioural choice (a new conflict status code, which side keeps a materialized pointer, whether a child entity follows a parent revision) is the failure mode — not the extra behaviour, which is usually better than a stall.
- **A child's deliverable can be REAL and still carry a FABRICATED identifier.** Existence/quality checks cannot catch this: the file is there, the diff is good, the child's own tests pass — but a pinned third-party ref inside it (GitHub action SHA, image digest, tool/library version, upstream commit) was invented at the token level, typically a plausible mid-string mutation of the true value, and the child's summary asserts it was "verified". Never accept that claim. Resolve every external reference the child introduced against its authoritative registry before committing (`gh api repos/<owner>/<repo>/commits/<sha> --jq .sha` echoes the sha only if it exists; `gh api repos/<owner>/<repo>/tags --jq '.[] | "\(.name) \(.commit.sha)"'` gives the real tag→commit map), then re-check every sibling file the same pin was copied into — a wrong pin propagates by copy. The fabrication is undetectable by inspection alone and surfaces only when a consumer resolves the ref, so the price of skipping this is a full push + CI cycle (a job failing at `Set up job` with `unable to find version`); resolving it orchestrator-side costs one API call.
- Re-`git add` files the child staged IF you modified them afterwards (lint fixes etc. → status shows `AM`, staged content is stale).
- **A child's own tests prove the new symbol works, not that it is registered.** When a child does additive-only work (adds a public function to a module it was told not otherwise to reshape), the orchestrator's independent re-read must check the module's public surface — `__all__`, re-exports — because a missing `__all__` entry passes every test the child wrote (they import the symbol by name, not via the export set) and only surfaces on a whole-file read or in a consumer that imports the public surface. Confirm the additive symbol actually made the module's export list before trusting the batch — check NEWLY ADDED public functions/generators too, not just classes: a streaming child adding a module-level convenience helper next to the class routinely omits it from `__all__`, and every in-module test (which imports by name) still passes. Grep the `__all__` list after any additive batch and add the missing names in the orchestrator's own commit. The same "green tests prove nothing about wiring" class covers contract and schema edits: a child that whitelists a new property in a JSON schema has proved NOTHING about the document it also changed. Grep the whitelisted key in the TARGET document first — a whitelist added to a document's schema that does not govern the edited file is inert, passes every test the child wrote, and hides that the new field has no validator at all. Accept such an edit explicitly as forward-looking documentation (and say so in the commit message), or move it to the schema that actually governs the file.
- Run the full suite + ruff + repo-conventions gate before pushing the batch.

## Late/stale async notifications after mainline takeover

When a provider outage forced mainline takeover of a batch's tasks, the batch still emits notifications afterwards: one early-warning per failed child ("task N/M failed, siblings still running") and a final "batch complete" — each can arrive MINUTES after mainline already executed the task. Every such notification is historical evidence, not a new instruction: (1) do NOT re-dispatch the named task; (2) verify mainline's deliverable is on disk at the exact path the original brief specified (existence + the brief's required verdict/field lines), and re-run its read-only checks against current HEAD because mainline work moved since the child froze; (3) only gaps absent on disk get re-done, centrally. A notification claiming "siblings still running" is unreliable too — the siblings are dead on the same dead pool; check `delegate_task action=list` and treat an empty list as "all dead, mainline owns everything".

## Pitfalls discovered in the field

- **Async results arrive against a STALE baseline.** A batch is dispatched at time T but its consolidated result re-enters the conversation minutes later, by which point the orchestrator (or another writer) may have committed/merged the very tree the children reviewed. Before acting on any finding, verify *which baseline the child actually froze*: check the dispatch time vs the child's stated HEAD/tree SHA vs the current `git rev-parse HEAD`. A batch that "reviewed main@<old-sha>" is evidence about that old sha only — it neither proves a gap still exists on current main, nor is it safe to dismiss as "already fixed" without re-checking. This session saw 4+ such batches all frozen on superseded SHAs; each had to be triaged by baseline, not by headline severity.
- Children's scripts may `sys.path.insert` project root → architecture guard `forbidden-sys-path-mutation` fails CI. Fix: importlib `spec_from_file_location` + `sys.modules` registration (see windows-development-environment "Cross-platform path & module traps").
- Children test on Windows locally; CI runs Linux. Windows-only path assertions (e.g. `os.path.isabs` on `C:/x`) pass locally, fail in CI — cross-platform guards required (same section).
- Children can produce code violating project-specific architecture guards (forbidden-absolute-path: hardcoded `C:\Program Files` etc.) — budget a guard-fix pass after merge.
- Write launcher/script files BEFORE background-launching them (launching first → "No such file or directory").
- A child that ran out of tool calls mid-verification leaves "all tests pass except the last step" — the orchestrator re-run covers it; do not treat the child's summary as final CI evidence.
- **Batch-wide API failure (HTTP 429 / rate limit) is a channel problem, not a task problem.** Parallel children multiply the provider's API calls; on a rate-limited or free-tier provider a wide fan-out can take down the WHOLE batch with 429s. When it happens: (1) do NOT re-dispatch the same batch expecting the limit to clear — it hits the same wall; (2) switch to central sequential execution on the orchestrator's own tool channel, which is unaffected by the subagent-provider limit and does the same work one item at a time; (3) size future batches to the provider's headroom. A transient external limit that killed the children does not make the task unsolvable — the orchestrator's channel still works, so finish the work centrally and mark the fan-out abandoned.
- **Root-cause the provider config BEFORE dispatching a wide batch, and HARVEST the dead children before re-doing anything.** Pre-dispatch: `hermes config get delegation` — if `delegation.model/provider` is a rate-limited free tier and `fallback_providers` is empty/`null`, a wide parallel fan-out WILL take the whole batch down on 429s: shrink the batch or probe candidate routing targets live first (`hermes chat -q "ping" --provider X -m Y -Q`; a 429/503 probe means the target is dead, and wiring a dead fallback only delays the failure). Post-failure: a child that died at the "send final answer" hop usually already has COMPLETE work products — the failed task's output in the batch consolidated message (status=failed tasks still carry their final JSON when the death happened at delivery, not mid-work), the live transcripts (tail technique above), and on-disk files. Integrate those products after cross-checking their evidence handles (SHAs, run IDs, file paths) against live state, and only re-run the gaps centrally. This is the mirror image of the fabricated-completion pitfall above: mid-work 429 output is untrustworthy, end-of-work 429 output is usually real work with a severed delivery — harvest, verify handles, fill the delta.
- **A child's HTTP 401 (auth rejected, not rate-limited) is a provider-credential problem, also a channel problem.** The child dies in seconds with "provider rejected your API key" before doing any tool call. Do NOT re-dispatch: the same credential wall will take down the re-dispatch identically. If the deliverable is self-contained (a few files + tests + one PR, the spec file already written), take it over on the mainline and execute it sequentially — the mainline's own model lane is unaffected by the subagent provider's credential state, and the spec file survives the abandoned batch. Re-dispatching only makes sense after the credential/provider is actually fixed, not after hoping the wall moves. Distinguish 401 from 429: 429 = transient, batch-size problem; 401 = the delegation provider's token is dead, nothing retries well until the user fixes the provider config. Either way the rule is the same — the orchestrator's central channel is the fallback, and it should be used, not treated as failure.
- **A truncated / externally-failed child can still emit a *fabricated* completion.** Under a 429 or tool-call exhaustion the child's last message may be a made-up "done: wrote files X/Y/Z, tests passed N" summary with no ground truth. Cross-check every claimed file path with `os.path.exists` before you integrate it OR before you believe the work landed; an absent path means that subtask did not happen — re-do it centrally. A failed child's partial output is the LEAST trustworthy report you have: treat it as unverified and confirm it against disk, never as done.

## Parallelism as passive orchestration (no second engine)

When the task is "add real-time parallel agent invocation / fan-out" on an existing executor federation or control plane, the deliverable is a design shape, not a new execution engine:

- Build a **passive orchestration layer**: a ThreadPoolExecutor fan-out that calls each adapter's existing ops and aggregates into the SAME typed result + the SAME receipt/evidence store. A second runtime, second ledger, or second result type violates the no-second-engine / no-second-updater rule and will be rejected on governance.
- Keep the registry passive: it must not spawn processes, read credentials, or apply policy. The threads only coordinate; each adapter keeps its own launch decision.
- **Per-route failure isolation is required**: one route's exception/timeout degrades only that route (ok=False, status FAILED/TIMEOUT); siblings continue. Aggregate statuses: OK (all) / PARTIAL (some) / DEGRADED (all degraded, no hard fail) / FAILED (all).
- Carry a **real-time event stream** (STARTED/DONE/FAILED/TIMEOUT per route) so callers monitor in-flight, not just the final aggregate.
- Disjoint files are the unit of parallelism: split so subagent A owns the orchestrator+tests and subagent B owns the contract/catalog registration - they touch no shared file, so they run concurrently without edit collision. A catalog-count change the B-side introduces is picked up automatically by any already-dynamic count assertion; confirm that assertion is dynamic, never hardcoded.
- **Shared contract with disjoint files:** when two children's work overlaps on a contract but not on files (one child extends the core module, the other builds a consumer or the schema against its current API), pin the shared surface in BOTH briefs verbatim: the child that extends gets "ONLY ADD new API; do NOT change signatures/return contract of <stable surface> — a sibling is building against it", the child that consumes gets the exact shape to code against (field names, statuses, partition lists), and the extending child's tests must include a regression guard that the stable surface still works unchanged. Without the pin, the extender silently reshapes the API and the consumer's shard fails on a file you did not run.
- **New module roots must be gate-discoverable:** adding a new tests/ (or service/) directory whose tests self-load siblings via `spec_from_file_location` bypasses the gate's module PYTHONPATH — fine for the tests' own imports, but the parent must still re-run the repo's authoritative gate with ITS OWN PYTHONPATH after collecting the children, and confirm the new modules appeared in the gate's dynamic discovery count. Self-reported green from an ad-hoc sys.path runner is not gate evidence.
- **Scratch runners are the sanctioned multi-root test path for children.** Where the guard wrapper blocks chaining a multi-segment PYTHONPATH inline, each child runs its new tests through a project-relative (git-ignored `.project-local/task-runtime/`) runner script that inserts the needed module roots into `sys.path` and invokes unittest on the new test modules; tell children this pattern in the brief so they do not burn tool calls fighting the wrapper. The runner proves behavior, NOT gate membership — the parent's full authoritative-gate re-run (previous rule) remains the only gate evidence.
- **Match the repo's schema dialect, not the task-pack wording:** before a child writes a new contract schema, have it read the validator class used by the sibling verifier (e.g. Draft202012 vs draft-07) and copy the `$schema` marker of its siblings; task-pack prose that names a dialect is a hint, not a spec — the verifier decides.

## CI wait-window batching

On repos with a slow full gate (Rust build, long E2E) plus a fast production gate: use the fast gate's completion at the exact head SHA as early evidence while the slow gate is still building, and dispatch the NEXT workstream's children into that wait window. Never commit the next batch on the fast gate alone — hold for the parent-side full local gate + the slow gate's conclusion at the pushed SHA, then merge the next batch. One slow-gate wait absorbed per workstream instead of serialized after every commit is where the parallelism speed actually comes from.

This section states WHAT to build and the invariants to hold; it is not a claim that an in-flight implementation passed - verify the child's fan-out code with an independent re-run before committing (see Verification above).
