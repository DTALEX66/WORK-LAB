## 1. The #138 CI flake: root cause and fix

- **Symptom** (run `36258544759`, first work-lab-gate on C head `20f42df`):
  `workflow-assistance` job red on
  `test_parallel_dispatch.ParallelDispatchOfTests.test_two_specs_all_ok`:
  `AssertionError: Lists differ: ['s2','s1'] != ['s1','s2']`; the re-run on
  the SAME commit (`36258547628`) passed → nondeterministic order flake,
  which left a stale failed `aggregate` check-run pinning the PR rollup.
- **Root cause** (implementation, not test): `services/execution-federation/parallel_dispatch.py`
  fills its per-spec `results` dict via
  `concurrent.futures.as_completed`, so the dict's iteration order is
  *completion* order (nondeterministic across thread scheduling). The batch
  summary then derived `succeeded` / `failed` / `notes` straight from
  `results.items()`, leaking completion order into the payload, while the
  P1 batch contract (and the fanout executor-level test, which pins input
  order `["a","b","c"]`) expects **input spec order**.
- **Fix**: build the summary from the input-order spec names (`results` used
  for lookups only). `as_completed` still drives concurrent execution; it no
  longer determines summary order. Commit: "Fix
  parallel_dispatch_of batch-summary determinism (root-cause of the #138 CI
  flake)" (C head `f905253` pre-rebase / `e2ed1df` post-rebase).
- **Regression negative controls** added to
  `tests/workflow-assistance/test_parallel_dispatch.py`:
  - `test_summary_order_is_input_order_even_when_completion_is_reversed`
    (a SlowAdapter spec that finishes last still reports in input order);
  - `test_failed_summary_stays_in_input_order` (failing spec reports
    failed/notes in input order).
- **Local determinism proof**: parallel-dispatch suite run 5/5 times, each
  `Ran 19 tests ... OK` (DETERMINISTIC_OK) — flake root-fixed, not green-once.

  full 7-job gate re-runs deterministically on Y. The red check-runs on
  `e2ed1df` no longer gate the merge (strict required check `aggregate`
  evaluates at the actual merge head Y).
